# Rebase Conflict UX V1

## Goal

Rebase V1 makes coordination decisions available from either the dashboard or the coding-agent chat. A user should not need to click a dashboard option and then manually tell an agent to fetch it. A paused agent should show the same actionable conflict choices as the dashboard, and either surface can record the user's approved decision.

## Product Principles

- Same-file edits are not automatically conflicts. Rebase should stop agents only when there is a genuine chance of integration failure.
- Compatible overlaps are coordination notices. They are visible, but they do not block work.
- Blocking conflicts require a user-approved direction. The first approved direction wins.
- Dashboard and agent chat are equal control surfaces.
- Raw diffs may be sent to OpenAI for classification when configured, but they are not persisted.

## User Experience

### Blocking Conflict In Agent Chat

When an agent checkpoints and Rebase finds a blocking conflict, the checkpoint response includes an action-focused brief:

- conflict title, risk, and short explanation
- affected peer agents and shared surfaces/files
- numbered choices matching the dashboard recommendations
- the recommended option and why
- what this agent would do for each choice

The agent pauses, presents the numbered choices, and can record the user's selected option through MCP. If the user chooses in the dashboard while the agent is waiting, the wait tool returns immediately with the chosen direction.

### Coordination Notice In Agent Chat

When an overlap is classified as additive-compatible, the agent reports a compact non-blocking notice and keeps working. The notice includes the compatible peer work and the recommended coordination plan, but it does not require a user choice.

### Dashboard Conflict Cards

Dashboard conflict cards show recommendations inline. Each card includes:

- risk label: `Blocking conflict` or `Coordination notice`
- affected agents, stale badges, and unreachable worktrees
- the model-recommended owner when ownership is needed
- editable direction text before sending
- buttons for numbered/recommended choices
- compact timeline showing chosen option, delivery, fetch, and acknowledgement status

The dashboard auto-generates recommendations when a conflict is detected. The old manual "Generate advisory" button can remain as a retry action, but the default state should already have choices.

## Compatibility Classification

Rebase keeps local detection fast and model-agnostic:

- worktrees
- changed files
- symbols
- surfaces
- normalized diff hashes

After local detection, Rebase classifies overlap compatibility.

Classification outcomes:

- `no_issue`: no user-facing item and no pause
- `coordination_notice`: visible non-blocking additive-compatible overlap
- `blocking_conflict`: destructive, ambiguous, or classifier-failed shared contract risk

OpenAI classification is preferred when `OPENAI_API_KEY` is configured. The classifier receives bounded scoped diff hunks, fingerprints, surfaces, symbols, and semantic summaries. The model returns a structured classification, rationale, recommended owner, recommended option, and per-agent plan summaries. Raw diff text is never stored in SQLite.

If OpenAI is missing or classification fails, Rebase falls back conservatively: shared contract risk becomes blocking; clearly unrelated or low-signal overlap remains non-blocking.

Examples:

- Two independent additions to a shared contract can be `coordination_notice` if the final contract can include both.
- Rename/delete/type-change of the same field is `blocking_conflict`.
- Conflicting route payload or migration behavior is `blocking_conflict`.
- Same file with unrelated import/logging changes is `no_issue`.

## Decision Lifecycle

The first user-approved decision locks the conflict. Later dashboard or agent-chat attempts receive an "already decided" response with the active decision.

Decision states:

- `active`: decision is locked and directions were queued
- `superseded`: reserved for future explicit override flows
- `cancelled`: allowed only before any target direction is fetched

Intervention delivery states:

- `queued`: direction exists and target has not received it
- `fetched`: checkpoint, wait, or fetch returned it to the target agent
- `acknowledged`: agent presented its 3-5 step plan in chat
- `cancelled`: direction was cancelled before fetch

Queued directions may be edited before any target fetches them. After any target fetches a direction, the user must create a follow-up intervention instead of editing the original.

Stale agents still receive queued directions, but the dashboard marks them as stale. Dirty worktrees with no joined agent are shown as unreachable; Rebase delivers to reachable agents and includes an explicit warning.

## Per-Agent Directions

Directions are complementary, not copied to every agent.

Owner direction:

- owns the final shared contract shape
- includes compatible peer intent when both features are desired
- checkpoints the final schema/type/API contract
- avoids editing peer worktrees

Adapter direction:

- pauses disputed contract edits while owner publishes/checkpoints
- preserves the owner contract shape
- adapts local feature work around the owner shape
- checkpoints after adaptation

Each direction includes role, conflict, peer summary, shared surfaces/files, and 3-5 concrete next steps.

## Coordinator Interfaces

Shared schemas add:

- compatibility classification result
- coordination notices
- conflict decisions
- decision options
- per-agent plan payloads
- intervention acknowledgement state

Coordinator APIs add:

- create locked decision for a conflict
- list choices for a session/conflict
- acknowledge an intervention
- wait for direction with timeout

Existing intervention APIs remain compatible. `rebase_fetch_intervention` continues to work, but checkpoint and wait are the normal delivery paths.

## MCP Interfaces

`rebase_checkpoint`:

- returns risk, notifications, non-blocking notices, blocking conflict choices, and queued directions
- marks returned queued directions as fetched
- pauses only for blocking conflicts

`rebase_wait_for_direction`:

- waits up to the requested timeout, capped at 120 seconds
- returns immediately when a dashboard or chat decision queues a direction
- on timeout returns current conflict choices and no direction

`rebase_record_decision`:

- records a user-approved numbered/dashboard-equivalent choice
- locks the conflict if no decision exists
- queues complementary per-agent directions
- returns the active decision if another surface already chose first

`rebase_acknowledge_intervention`:

- marks a fetched direction as acknowledged after the agent presents its plan

`rebase_fetch_intervention`:

- remains a compatibility alias for fetching queued directions

## Dashboard Implementation Notes

The dashboard should remain an operational tool, not a marketing surface. Use dense, scan-friendly layout, clear status labels, and restrained styling. Conflict cards should be action-first: the user should understand the recommended decision and its consequences without opening another page.

For V1 MVP, inline cards are enough. A separate conflict detail page can come later if audit history becomes too large.

## Testing Strategy

- Classifier tests cover additive-compatible, destructive, ambiguous, unrelated, and model failure fallback.
- Conflict detection tests prove harmless same-file edits do not block agents.
- Decision tests prove first choice wins and fetched interventions cannot be edited in place.
- MCP tests prove checkpoint returns directions, wait returns immediately or times out with choices, record-decision locks, and acknowledgement updates state.
- Dashboard/action tests prove inline choice submission queues owner and adapter directions and exposes lifecycle state.
- Full verification: `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build`.
